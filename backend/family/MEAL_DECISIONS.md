# Family meal decisions

The `mealDecision` callable requires the same Google account and App Check as the other family callables. Every request includes an `action`; no action accepts a family or child identifier. Times are server milliseconds since the Unix epoch. A request ID and source ID are 32 lowercase hexadecimal characters. The meal ID is the decimal ID of the child's mirrored meal.

- `configure`: `{action, enabled}` enables or disables a caregiver's participation. The default is disabled.
- `create`: `{action, requestId, mealId, sourceId, timeoutFallback, allowManualDecision}` is child-only. `timeoutFallback` is `app` or `manual`. `allowManualDecision` defaults to true when omitted; false cannot be combined with a manual fallback. Creation is idempotent for identical parameters and captures the current meal revision and a five-minute deadline. If another request is already active for the same child, source and meal, create returns that request instead; use the returned requestId.
- `fetch`: `{action}` returns `{ownerUid, sourceId, requests, caregivers, enabled}` for the current family. It returns at most 50 recent requests. Requests include `id`, `mealId`, `mealName`, `mealRevision`, `sourceId`, `ownerUid` (the child), `createdAt`, `deadline`, `status`, `claimedByUid`, `claimedByName`, `claimAvailable`, `stage`, `presentUntil`, `members`, `response`, and `outcome`. Status is `waiting`, `answered`, `accepting`, `accepted`, or `expired`. Expiration is computed on read even if no client has recorded the fallback yet.
- `claim`: `{action, requestId}` takes a 30-second caregiver lease. `heartbeat`: `{action, requestId, stage, present}` renews it, with stage `context` or `decision`; `present: false` marks the owner inactive while retaining ownership until the existing lease expires. The owner remains visible after expiry; `claimAvailable` then allows another caregiver to claim it. The former owner can renew on return if nobody has taken over. Only an active owner can delegate or respond.
- `decline`: `{action, requestId}` declines for that caregiver. When every currently enabled caregiver has declined, the server immediately marks the request expired with `terminalReason: allCaregiversDeclined`, retains the declined roster, and signals the child. `delegate`: `{action, requestId, caregiverUid}` transfers ownership to an eligible current caregiver.
- `respond`: `{action, requestId, decision}`. Decision is `{type, minutes, message, targetSuggestion}`; `type` is `insulinThenWait`, `insulinAndEat`, `eatThenInsulin`, or `deferMeal`; `minutes` is null or an integer from 1 to 180 and is required for `insulinThenWait` and `deferMeal`. Message is a string of up to 240 characters; targetSuggestion is null or a string of up to 240 characters. The server supplies caregiver identity and `respondedAt`. Suggestions do not themselves change treatment or the meal.
- `prepareAcceptance`: `{action, requestId, sourceId}` validates the response, membership, meal revision and deadline, and durably reserves acceptance. It returns `{requestId, acceptanceToken, acceptanceUntil}`; persist the token before applying the response locally. The same token is returned on retries. `acceptanceUntil` is advisory metadata and does not expire the reservation. The child must either acknowledge local success or explicitly abort with the token.
- `abortAcceptance`: `{action, requestId, sourceId, acceptanceToken}` cancels an uncommitted reservation. Only call after proving no local receipt was committed. This sets status `expired` without an outcome and preserves only a token hash for idempotent retries. After the original deadline, `expire` records the fallback without the token.
- `acknowledge`: `{action, requestId, sourceId, acceptanceToken, outcome}` records a successfully applied caregiver decision, even after the deadline. Outcome is `{source:'caregiver', decision, minutes, caregiverUid}` and must match the response. Call only after the local operation succeeds. It is idempotent for the same outcome.
- `expire`: `{action, requestId, sourceId, outcome}` records the actual fallback after the deadline, or immediately after the server records `allCaregiversDeclined`. A prepared acceptance can only be replaced by a fallback if the child explicitly aborts it first. Outcome is `{source:'mealAdvisor'|'manual', decision, minutes, caregiverUid:null}` The app source is always available; the manual source is allowed only when the captured manual permission is enabled. It is idempotent for the same outcome.

Mutations return the stored record, whose internal statuses are `open`, `responded`, `acknowledged`, and `expired`; clients should fetch the normalized view after a mutation. The server validates membership, opt-in, source and meal revision at the applicable transitions. Responding after the deadline is rejected. A prepared acceptance may be acknowledged after the deadline, including after a long offline period; an already acknowledged receipt remains idempotent. No background expiration worker is needed for enforcement.
